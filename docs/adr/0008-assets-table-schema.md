# 0008. 同期状態を assets テーブルで「現在の状態」として管理する

- ステータス: 承認済み（チェックサム列は [0009](0009-no-local-checksum.md) で削除）
- 日付: 2026-03-07

## 背景

- ファイルごとの同期状態（成功・同期中・失敗）を保持したい
- 失敗の理由と回数も保持したい

## 決定

- 1 ファイル 1 行の `assets` テーブルで、ファイルの**現在の状態**を管理する
- 現在のスキーマは `internal/db/db.go` を正とする

### テーブルの設計方針

- **イベントログ型ではなく現在状態管理型にする**
  - 主な用途が「今の同期状態の確認」のため
- **物理削除にする**
  - 削除履歴を参照するユースケースがない
  - 同じファイルが再追加されても、Immich 側が duplicate と判定する
  - そのため、履歴を残さなくても二重にアップロードされることはない
- **インデックスは `UNIQUE` 制約で自動作成されるものだけにする**
  - `status` はカーディナリティが低く、インデックスの効果が薄い
- **マイグレーションツールは導入しない**
  - 起動時の `CREATE TABLE IF NOT EXISTS` でテーブルを作る
  - 列の追加は、軽量なマイグレーション関数で対応する
  - golang-migrate などは今の規模では不要

### 列ごとの判断

- **`status` 列 + `CHECK` 制約**（`success` / `syncing` / `failed`）
  - 「状態列はアンチパターン」とされるのは、次のようなケース
    - 状態が複数の列にまたがる
    - 遷移が複雑で DB で制御できない
    - 意味が曖昧
  - 本件はいずれにも当てはまらない
  - `synced_at` / `failed_at` のようにタイムスタンプで状態を表す案は採らなかった
    - 状態を追加するたびに列が増えるため
  - 将来 `pending`（アップロード待ち）などを追加するときは、`CHECK` 制約を更新する
- **`immich_id`（NULL 可）**
  - Immich 側のアセット ID で紐付ける
  - アップロードに失敗したときは NULL
- **`immich_status`**（2026-09-23 追加）
  - Immich のアップロードレスポンスの status（`created` / `duplicate` など）を記録する
- **`latest_failed_reason`（デフォルト NULL）**
  - NULL は「失敗していない」を表す
  - 空文字は「理由不明の失敗」を表す
- **`created_at` / `updated_at`**
  - UTC で保存し、UI での表示時にローカル時刻へ変換する

## 結果

- スキーマが単純で、クエリも読みやすい
- 状態の変更履歴は DB には残らない
  - 履歴は同期ログ `sync.jsonl` で追う
